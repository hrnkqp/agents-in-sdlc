プロジェクトに小さな機能を追加しました。より大規模な変更には、堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のワークフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。issue を使って新機能を作成し、コードが有効で、機能が期待どおりに動作することを確かめて、最終的にプロジェクトにマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使います。通常、作業するファイルの種類ごとに異なるセッションや PR を使用しますが、ここでは主な概念に集中できるよう簡略化します。

このレッスンでは、次のことを行います。

- GitHub issue からエージェントセッションを開始します。
- **Plan** モードで要件を決めます。
- **Autopilot** モードで新機能を実装します。
- コードをレビューします。
- ブラウザーキャンバスで機能を手動で検証します。

この機能の作業を続ける中で、リポジトリの指示を更新し、既存の `quality-checks` スキルをカスタマイズし、MCP による検証を追加して QA エージェントを作成し、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、利用者はカテゴリと publisher でゲームを絞り込みたいと考えています。バックログの issue には機能が記載されていますが、カテゴリを組み合わせる方法など、コーディング前に合意が必要な詳細もあります。Plan モードで決定し、Autopilot に範囲を限定した実装を許可します。

## 背景

AI コーディングエージェントを開発に取り入れても、基本は変わりません。むしろ、より重要になります。多くの開発者は、次のような流れで作業します。

1. 必要な作業の詳細が記載された issue を開きます。
2. 構築する内容を計画します。
3. コードを作成してレビューします。
4. テストを実行してコードを検証します。
5. 新機能を手動で検証します。
6. プルリクエスト (PR) を作成します。
7. コードレビューが完了し、継続的インテグレーションプロセスが成功したら、コードをマージします。

> [!NOTE]
> 手順の詳細はチームや組織によって異なりますが、ほとんどは上記の流れに沿っています。

標準的な方法を守ることで、AI が生成したコードが要件を満たし、手作業で作成したコードと同じレビューと検証を受けるようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: エージェントと一緒に作業します。エージェントは変更を提案し、次の操作に進む前に入力を待ちます。
- **Plan**: エージェントが計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律的に作業し、入力を待たずにコードを書き、テストを実行して反復します。

まず Plan モードで計画を確認し、その後 Autopilot で実装します。

## issue からセッションを開始する

開始前に、星評価の PR がマージされ、ローカルの `main` が最新であることを確認します。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリフォルダーを選択し、リポジトリの上部ナビゲーションで **Issues** を選択します。既存の **Allow users to filter games by category and publisher** issue を開きます。テンプレートで準備されている issue なので、新しく作成する必要はありません。
2. **New session** を選択し、更新した `main` を基にした **new working tree** を選びます。

    ![GitHub Copilot app の issue ビューで New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. issue がセッションに添付されていることを確認し、モード選択から **Plan** を選びます。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは動かない場合、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了してから再起動します。失敗した操作とチェックを再実行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルタリング機能を計画する

計画を立てると、Copilot がコードを書く前にアプローチを確認できます。issue から開始したため、Copilot は機能リクエストをすでにコンテキストとして把握しています。次のプロンプトを送信します。

```plaintext
Build this feature.
```

Copilot の質問に回答し、issue の受け入れ条件と計画を比較します。カテゴリと publisher のフィルタリング、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認してください。複数カテゴリの組み合わせ方法や、ゲームが見つからない場合の動作など、不明確な内容について話し合います。

計画には、プロジェクトの既存ツールを使った lint、ユニットテスト、E2E テスト、型チェックを含めます。フィルタリングの実装とテストに範囲を絞り、品質ワークフローを終えてから PR を作成します。計画の変更は承認前に依頼し、後で検証できるよう issue の URL と合意した補足事項を控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、**Approve and implement this plan** または使用中のバージョンに表示される同等のオプションを選択します。承認するとモードも切り替わると決めつけず、現在のモードを確認してください。モード表示が **Autopilot** になっていることを確認します。

Copilot が実装を始めます。作成した計画に沿って作業し、コードを生成してテストを実行しながら反復します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画を確認してください。依存関係が不足している、ポートが競合しているなどの報告があれば、チェック完了と見なす前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードは、他のコードと同じようにマージ前にレビューします。コードを確認し、サイトを起動して動作も確かめましょう。

1. **Changes** を開き、フィルタリングの実装とテストを確認します。
2. 複数カテゴリと publisher の組み合わせも含め、結果を issue と承認済みの追加の取り決めに照らし合わせます。変更が既存のリポジトリの指示に従っていることを確認します。
3. lint、ユニットテスト、E2E テスト、型チェックの結果を確認します。スキップされたチェックは成功ではありません。
4. 変更を採用する前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 構成はプレビューをビルドして実行し、ローカルサーバーを再利用する場合があります。テスト対象が前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

コードに問題がないように見えても、実際に動くか確認しましょう。アプリを起動し、ブラウザーキャンバスでサイトを開きます。

1. 次のプロンプトを使い、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. しばらくするとアプリが起動し、Copilot app 内にブラウザーウィンドウが開きます。
3. カテゴリを選択し、表示結果がそのカテゴリに合うことを確認します。フィルターを解除して publisher を選択し、結果が一致することを確認します。
4. カテゴリと publisher を組み合わせ、issue と承認した計画に照らし合わせて結果を確認します。複数カテゴリがサポートされる場合は、合意した組み合わせ動作を確認します。
5. ゲームが見つからないフィルターの組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、一覧全体が戻ることも確認します。
6. 確認が終わったら、次のプロンプトを使って、このセッションで起動した開発サーバーを停止するよう Copilot に依頼します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに備えてセッションを保持する

まだフィルタリング PR を作成したりマージしたりしないでください。レッスン 4 から 8 まで、このセッション、worktree、ブランチを使います。次はカスタム指示をフィルタリングコードに適用し、スキルと QA の改善を追加してから、レッスン 8 で PR を作成してマージします。開発サーバーを停止した後、セッションを終了せずに待機状態にしておき、次のレッスンで同じセッションに戻ります。
